# 项目原始目标基线（Intent Baseline）

> 本文件回答：项目最初为什么启动、用户希望最终解决什么问题。
> 它不是任务清单、当前进度或 Agent 的自由发挥空间。确认后不得静默改写；后续变化追加到同目录的 CHANGES.md。

## 基线元信息

- 基线版本：B1
- 状态：draft（仅在用户明确确认后改为 confirmed；既有项目反向梳理标记为 adopted）
- 建立日期：YYYY-MM-DD
- 来源：user_request | user_confirmed | project_adoption
- 来源说明：引用需求文档/用户明确表述/可核验的项目材料；不要粘贴完整聊天记录

## 项目问题

用事实描述项目为何存在、当前要解决的根本问题。区分用户明确陈述与 Agent 推断；推断必须标为待确认。

## 目标（稳定 ID，不复用）

| ID | 目标结果 | 优先级 | 来源/确认状态 | 可验证成功判据 |
|---|---|---|---|---|
| G001 | （用户希望得到的可观察结果，不写实现任务） | P1 | user_request / confirmed / needs_confirmation | （如何证明目标达成） |

目标 ID 使用 G001、G002……。一个目标描述一个结果；不要把任务、技术方案或临时 Bug 直接写成目标。

## 核心约束

- 必须满足：
  - （兼容性、业务、安全、性能、预算、技术边界等）
- 明确不做（Non-goals）：
  - （明确排除的范围及原因）

## 基线确认

- 确认状态：pending
- 用户确认记录：YYYY-MM-DD / 确认方式 / 确认范围
- 未确认项：列出仍需用户裁定的推断或歧义

## 维护规则

1. 初次建立时，Agent 可以根据用户明确需求起草；不得把推断包装成用户承诺。复杂/长期项目在大规模实施前应请用户确认关键目标与成功判据。
2. 确认后，本文件作为原始基线只读保存。拼写等不改变含义的修正可直接修；目标、约束、范围或成功判据变化必须在 CHANGES.md 追加记录。
3. 新目标使用新 ID；不得复用已撤回、完成或被替代的 ID。
4. 既有项目没有可追溯的原始需求时，标记 adopted，依据当前代码、文档和用户确认反向建立；不得伪称为最初用户原话。
5. 本文件不记录任务进度、会话摘要或完整对话；进度归任务索引/卡片，当前断点归 .memory/MEMORY.md。
