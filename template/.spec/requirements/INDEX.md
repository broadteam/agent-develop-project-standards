# 需求索引（Requirement Registry）

> 本文件是可验证需求的唯一登记处。它把用户目标转成可交付、可验证的要求；不是把每个任务都包装成需求。
> 仅长期、跨任务、影响用户目标或需要独立验收的要求分配 R ID。纯内部重构/维护任务可直接关联 G 或标记 supporting。

## 需求状态

| 状态 | 含义 |
|---|---|
| proposed | Agent 提议或尚未确认，不得当作用户承诺 |
| accepted | 用户明确提出或确认，进入范围 |
| in_progress | 已有任务正在实现 |
| implemented | 实现已完成，但尚无充分验证证据 |
| verified | 验收判据已由有效 V 记录证明 |
| deferred | 用户确认暂缓，保留需求与原因 |
| withdrawn | 用户明确撤回，保留历史与来源 |

## 维护规则

1. 先确认目标，再判断是否需要独立需求。一个目标可拆成多个需求；一个需求可支持多个目标。不得为每张任务卡机械创建需求。
2. accepted 只能来自用户明确表达或确认；Agent 建议必须保持 proposed，直至用户确认。
3. 验收判据必须可观察、可重复验证。避免“体验良好”“性能优秀”等不可判定表述。
4. 需求范围或验收变化时，先在 .spec/intent/CHANGES.md 追加 C 记录，再更新本索引并引用 C ID。不得覆盖历史意图。
5. implemented 不等于 verified。只有存在有效 V 记录且其结果覆盖该需求的验收判据，才可标记 verified。
6. deferred / withdrawn 必须有对应用户确认的 C 记录；Agent 不得自行将未完成需求移出范围。
7. 不直接关联用户目标的基础设施/维护需求，目标列写 supporting: <说明>；不得为了通过检查虚构 G ID。
8. 当索引变大时，将详细背景和复杂验收拆入 Rnnn/requirement.md，索引仍保留状态、目标、来源和验证指针；不要复制整段需求到任务卡。

## 需求详情模板

复杂需求可建立 .spec/requirements/Rnnn/requirement.md，至少包含：

- 用户可观察结果与适用边界
- 关联 Gnnn / Cnnn
- 明确不包含的内容
- 可验证验收判据（每项独立编号）
- 依赖与风险
- 验证证据 Vnnn 指针

简单需求不需要详情目录。
