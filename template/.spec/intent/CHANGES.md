# 项目意图变更账本（Intent Change Ledger）

> 只记录会影响目标、需求、范围、成功判据、关键约束、优先级或关键决策的对话增量。
> 本账本是追加式记录：不得静默改写或删除既有记录；纠错、撤回和替代均新增记录并引用原 ID。

## 分类

| 类型 | 含义 | 默认处理 |
|---|---|---|
| clarification | 澄清已有目标/需求，不改变其含义 | 更新理解；只有影响验收时才调整任务 |
| correction | 修正用户原需求或 Agent 对需求的错误理解 | 记录正确表述与失效理解 |
| addition | 增加此前未包含的新目标/需求 | 分配新 ID，评估是否进入当前范围 |
| scope_change | 改变已有目标的范围或成功判据 | 记录前后差异；影响不明确时请用户裁定 |
| reprioritization | 调整目标顺序或优先级 | 不等于取消其他目标 |
| defer | 暂缓目标/需求 | 保留目标与原因，不标记完成或撤回 |
| withdrawal | 用户明确不再需要某目标/需求 | 标记撤回，保留历史与原因 |
| restore | 恢复此前暂缓/撤回的目标 | 引用原目标/变更 ID，说明恢复依据 |

临时排障、实现细节讨论和不改变长期意图的局部修复通常不进入本账本；如它改变了长期需求或验收，则必须记录。

## 每轮对话的意图检查协议

> 目的不是记录每句话，而是在采取行动前识别它是否改变长期方向，并在临时插单结束后找回原来的工作。

1. **恢复当前锚点**：处理跟踪任务前，先从 BASELINE、已 accepted 的 CHANGES、任务/里程碑索引和 MEMORY §0 确认当前目标、需求、工作项、待裁定事项与下一步。缺少信息时标记未知并查证，不得补造。
2. **对新消息分类**：
   - `continuation`：继续当前目标，不新增 C 记录。
   - `clarification`：仅当改变需求理解或验收时记录。
   - `bounded_interruption`：临时排障、局部修复或一次性插单；独立处理，不自动改变长期目标、里程碑顺序或原任务状态。
   - `intent_change`：明确新增、撤回、改范围或改优先级；按记录模板追加 C 记录。
   - `conflict_or_ambiguity`：与现有目标、约束或验收冲突，或用户未明确取舍；不得自行选择新方向。
3. **区分用户决定与 Agent 建议**：用户明确提出/确认的变化可记录为 `user_explicit` / `user_confirmed`；Agent 推断或建议只能是 `agent_proposed` 且 `pending`。pending 不进入当前有效意图，也不能据此重排任务。
4. **保护中断现场**：开始会暂停当前跟踪工作的插单前，在 MEMORY §0 保留原目标/需求/任务 ID、暂停原因和恢复后的下一步；插单完成后先恢复该断点，不要把插单当作新主线。
5. **冲突时只暂停冲突决策**：继续不受影响的工作；对无法推导的范围或优先级取舍，只向用户提出一个最关键的澄清问题。不得把沉默、最近一次讨论或 Agent 的“更合理方案”视为确认。
6. **只更新对应权威来源**：原始基线不因新对话而改写；意图变化追加 CHANGES；任务状态改任务索引；执行断点改 MEMORY；验收证据写 verification。不要在多个文件复制同一份“当前目标清单”。
7. **恢复与收口做偏离检查**：恢复时比较当前工作与基线、适用的 accepted 变更及任务验收；收口时说明原计划是否偏离、偏离原因、是否影响目标/需求。局部任务完成不能自动关闭目标或里程碑。

## 意图对齐审查协议（任务开工与收口）

> 对齐审查检查“实际交付是否仍在解决用户要解决的问题”，不是再次复制需求，也不是让 Agent 自己写一句“符合预期”就算通过。

### 开工前

对标记 `意图对齐：required` 的跟踪任务，在进入 `in_progress` 前完成任务卡的「开工意图对齐」：

- 从 BASELINE、所有适用的 accepted CHANGES 和关联需求中重新读取目标，不以最近几轮对话或上一会话摘要代替。
- 写明本任务关联的 G/R、当前适用的 accepted C、预期贡献，以及本任务必须保留的约束。
- 预期贡献必须描述对目标/需求的可观察推进，不要只写“修改某模块”“重构代码”。
- 任务卡未关联需求时可以只关联目标；纯支撑任务用 `supporting:` 说明支撑关系，不虚构 G/R。`意图对齐：not_applicable` 仅用于不直接服务目标/需求的纯支撑任务，必须写豁免原因；有 G/R 关联时不得豁免。

### 收口前

任务进入 `review` 或 `done` 前完成「收口意图对齐」，至少检查：

1. 实际 diff 是否落在任务范围内；有没有顺手扩大范围、遗漏原定交付或改变外部行为。
2. 实际实现是否仍满足 BASELINE、适用的 accepted C 和需求验收；不能只根据任务标题判断。
3. 计划与实际差异是什么，为什么发生；对应代码提交和验证证据在哪里。
4. 对目标/需求的影响是什么，是否需要新增任务、补充验证或更新 accepted C。

结论使用以下枚举：

| 结论 | 判定 | 后续 |
|---|---|---|
| `aligned` | 实际结果符合预期贡献与既定验收，无实质偏离 | 可以按正常验收收口 |
| `justified_adjustment` | 实现路径与原计划不同，但用户目标、范围和验收没有改变 | 记录差异与技术理由；不修改原始目标 |
| `user_confirmed_change` | 实际范围/验收/目标变化已由用户明确确认 | 关联 accepted C；同步受影响的 R、任务和里程碑 |
| `unresolved_drift` | 不能证明实际交付仍符合目标，或偏离需要用户裁定 | 不得标记任务 done；保留 blocked/review 状态并提出最关键的裁定问题 |

### 里程碑关闭

- 新建/纳入本治理版本的里程碑默认 `意图对齐：required`；旧里程碑未声明该字段时不被追溯性阻断。若声明 `not_applicable`，必须说明原因；有直接目标/需求关联的里程碑不能豁免。
- 里程碑状态改为「已完成」前，必须填写「里程碑意图对齐回顾」：逐项对照目标成功判据、实际交付与完整 Commit SHA、需求验收覆盖、偏离结论、未解决漂移和后续动作。
- 关联需求必须全部为 `verified`，或有用户确认的 `deferred` / `withdrawn` 决策；`verified` 需求必须有覆盖该 R 的 `pass` V 证据，暂缓/撤回必须引用 accepted C。
- 里程碑结论为 `unresolved_drift` 或「未解决漂移」不为「无」时，不得标记已完成。里程碑包含的任务必须为 `done` 或 `dropped`；`dropped` 任务必须能追溯到 accepted C。
- 自动检查只验证状态、引用、commit 和证据链，不替代 Agent 阅读实际代码 diff、目标判据与测试结果的语义审查。

### 证据边界

- 收口必须记录实际实现的完整 commit SHA；不改代码的工作写明 `no-code: 原因`。
- 有正式需求验收时引用 Vnnn；引用的 V 必须覆盖该任务至少一项关联需求，并与收口审查的 Commit SHA 一致。没有独立 V 记录时，写明可复现任务级命令/步骤及结果，不要伪造 V。
- `user_confirmed_change` 必须有 accepted C 记录；Agent 建议、猜测或“用户似乎同意”不算确认。
- 语义判断必须对照具体代码 diff、测试结果和验收标准。校验器只能检查字段、ID、状态和证据指针，不能证明实现本身正确。
- 轻量任务不强制创建任务卡或执行完整审查；当轻量任务扩大为跟踪任务，或触及架构、数据、权限、对外契约时，必须补齐开工锚点再继续。

## Agent 处理规则

1. 先判断用户新内容是补充、纠正、新增、范围变化、优先级变化、暂缓、撤回还是恢复；不要把最近一轮对话默认当成最高优先级的项目目标。
2. 仅用户明确表达或确认的内容可标记为 accepted。Agent 的推断/建议标记为 agent_proposed / pending，不得自行升级为用户决定。
3. 用户要求处理一个临时问题，不代表用户放弃或替换原计划。先解决不冲突的局部问题；若确实影响既有目标、范围或优先级，再记录并说明影响。局部修复不代表整体目标完成。
4. 新需求不自动挤掉旧目标；目标冲突、成功判据冲突或范围取舍无法从用户表达中确定时，暂停该项取舍并向用户提一个明确问题。
5. 纠正、撤回、恢复和替代均追加新记录，使用 superseded 指向被替代记录；不得通过编辑旧记录制造“从未发生”的历史。
6. 不复制聊天全文。记录足以解释变化、来源、决定及其影响的最小摘要。
7. 任务卡使用 goal_refs / change_refs 关联本账本；不相关的维护任务可标记 supporting 并说明支撑关系，不得臆造目标 ID。
8. 每次跟踪任务恢复、里程碑收口、阶段切换、会话交接或项目完成评估时，核对原始目标、已接受变更、待确认事项与实际验证证据。
