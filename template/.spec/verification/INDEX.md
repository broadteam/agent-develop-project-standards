# 验证证据索引（Verification Evidence）

> 本文件记录可追溯的验证事实，不记录“我觉得完成了”。一个 V 记录可以证明多个 R；一个 R 也可以由多个 V 共同证明。
> 证据必须能定位到具体实现版本，不能只写“测试通过”。

## 证据记录

| ID | 覆盖需求 | 验证类型 | 结果 | 证据位置 |
|---|---|---|---|---|
| V001 | R001 | automated_test / manual_check / CI | pass / fail / partial | （命令、报告或 CI URL） |

## 记录模板

### V001 — 简短验证名称

- 日期：YYYY-MM-DD
- 覆盖需求：R001
- 验证类型：automated_test | manual_check | CI | production_observation
- 结果：pass | fail | partial
- Commit：完整 SHA（必须是被验证的代码版本）
- 执行环境：OS、运行时/版本、关键配置
- 命令/步骤：可重复执行的命令或人工操作步骤
- 证据：CI run URL、测试报告路径、日志路径或人工检查记录
- 判定：逐条对应需求验收判据，说明通过/失败/未覆盖项
- 限制：未覆盖的场景、已知缺陷、证据有效边界

## 证据规则

1. V ID 使用 V001、V002……，全项目唯一且永不复用；同一轮验证可覆盖多个需求。
2. 必须记录被验证的 commit SHA。CI URL 应指向该 commit 的实际运行；不得把其他提交的绿灯移植为当前提交的证据。
3. pass 仅表示所列覆盖范围通过，不自动证明整个需求或目标完成；需逐条映射验收判据。
4. partial 不足以将需求标记为 verified；fail 应保留并链接修复任务，不得删除失败历史。
5. 手工验证需记录操作者可复现的步骤和观察结果；只有结论、没有步骤的“手测通过”不算充分证据。
6. 不为每次本地小测试都创建 V 记录。只有用于需求验收、里程碑收口、发布决策或重要风险裁定的证据才入账。
7. 证据记录是事实账本；修正或补充通过新增记录，并引用旧 V ID，不静默改写历史。
