## 4. 版本号

`MAJOR.MINOR.PATCH`：

| 位 | 什么时候涨 |
|---|---|
| **MAJOR** | 破坏兼容。**改应用标识属于 MAJOR 级**——会动用户数据目录，必须带迁移 |
| **MINOR** | 新增能力，旧用法仍然有效 |
| **PATCH** | 只修 bug，不加能力 |

### 只在发布时改，不是每次提交都改

判断标准一句话：**这次改动要不要让使用者知道"该升级了"？**

- 开发过程中的连续提交 → **不动版本号**
- 一次发布（打 tag + CHANGELOG 定稿）→ 才改

把每次提交都当发布，结果是版本号一天涨五次，等于没有版本——使用者无法从版本号判断"值不值得升"。

### 版本号必须与 git tag 一致

文件里写着 `2.4.0` 却没有 `v2.4.0` tag，等于对外承诺了一个不存在的版本。

### 开发期不改版本，下游怎么判断该不该更新

靠**文件哈希**，不靠版本号。升级工具比对每个文件的 `installed_sha256`，版本号只是给人看的标签。

所以：升级时把目标指向**已发布的 tag**，不要指向还在动的开发分支。

### CHANGELOG 写什么

每个版本一段，只写**使用者需要知道的**：新增什么、修了什么、有什么已知限制。

不要写"优化了代码结构""重构了模块"——那是内部视角，使用者不关心，写多了反而淹没真正重要的变更。

已知限制必须写。**不写不等于没有，只等于别人不知道。**
