# 项目意图变更账本（Intent Change Ledger）

> 只记录会影响目标、需求、范围、成功判据、关键约束、优先级或关键决策的对话增量。
> 本账本是追加式记录：不得静默改写或删除既有记录；纠错、撤回和替代均新增记录并引用原 ID。

## 分类

| 类型 | 含义 | 默认处理 |
|---|---|---|
| clarification | 澄清已有目标/需求，不改变其含义 | 更新理解；只有影响验收时才调整任务 |
| correction | 修正用户原需求或 Agent 对需求的错误理解 | 记录正确表述与失效理解 |
| addition | 增加此前未包含的新目标/需求 | 分配新 ID，评估是否进入当前范围 |
| scope_change | 改变已有目标的范围或成功判据 | 记录前后差异；影响不明确时请用户裁定 |
| reprioritization | 调整目标顺序或优先级 | 不等于取消其他目标 |
| defer | 暂缓目标/需求 | 保留目标与原因，不标记完成或撤回 |
| withdrawal | 用户明确不再需要某目标/需求 | 标记撤回，保留历史与原因 |
| restore | 恢复此前暂缓/撤回的目标 | 引用原目标/变更 ID，说明恢复依据 |

临时排障、实现细节讨论和不改变长期意图的局部修复通常不进入本账本；如它改变了长期需求或验收，则必须记录。

## Agent 处理规则

1. 先判断用户新内容是补充、纠正、新增、范围变化、优先级变化、暂缓、撤回还是恢复；不要把最近一轮对话默认当成最高优先级的项目目标。
2. 仅用户明确表达或确认的内容可标记为 accepted。Agent 的推断/建议标记为 agent_proposed / pending，不得自行升级为用户决定。
3. 用户要求处理一个临时问题，不代表用户放弃或替换原计划。先解决不冲突的局部问题；若确实影响既有目标、范围或优先级，再记录并说明影响。
4. 新需求不自动挤掉旧目标；目标冲突、成功判据冲突或范围取舍无法从用户表达中确定时，暂停该项取舍并向用户提一个明确问题。
5. 纠正、撤回、恢复和替代均追加新记录，使用 superseded 指向被替代记录；不得通过编辑旧记录制造“从未发生”的历史。
6. 不复制聊天全文。记录足以解释变化、来源、决定及其影响的最小摘要。
7. 任务卡使用 goal_refs / change_refs 关联本账本；不相关的维护任务可标记 supporting 并说明支撑关系，不得臆造目标 ID。
8. 每次跟踪任务恢复、里程碑收口、阶段切换、会话交接或项目完成评估时，核对原始目标、已接受变更、待确认事项与实际验证证据。
