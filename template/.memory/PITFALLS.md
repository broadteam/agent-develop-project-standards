# 判据与实证（只增不改结论）

> 每条都是**真实踩过**的，不是想象中的风险。新坑追加到末尾，编号不复用。
> 格式：现象 → 根因 → 对策。写不清根因的，说明还没定位，别急着记。

## 环境与工具

- **P1 删除命令可能被安全垫片拦截**。某些环境会把 `rm` / `Remove-Item` 接管为"先送回收站"，目标过大或文件被占用时回收站失败，于是**拒绝降级为永久删除**。表现为"删不掉"，实际是保护机制在拦。对策：先释放占用，再删；确需强删时由用户手动操作，不要用其他命令绕过。
- **P2 目录被当前进程占用时无法重命名或删除**（`Device or resource busy`）。对策：先把工作目录切走，或关掉占用它的应用。
- **P3 网络路径（UNC / 挂载盘）上写入可能失败**。只读浏览通常没问题，写入改用本地路径或脚本重定向。

## 版本控制

- **P4 换行符会毁掉 shell 脚本**。Windows 上 `core.autocrlf` 把 `.sh` 转成 CRLF 后，shebang 变成 `#!/bin/sh\r`，报 "required file not found"。对策：`.gitattributes` 里对 `*.sh` 固定 `eol=lf`。
- **P5 文件模式位丢失**。跨文件系统拷贝后脚本失去可执行位，`git add` 会记成 644。对策：`git update-index --chmod=+x <file>`，并 `git config core.fileMode false`。

## 依赖与构建

- **P6 构建产物散落是灾难**。每次迭代留一份 `out2`/`out8`，几轮就占几个 G，且不知道哪份是最新。对策：产物只留一个目录，旧包归档到项目外，并在治理检查里禁用序号目录。
- **P7 改包名/应用标识会改变用户数据目录**。改名后老用户看到"数据全没了"（其实在旧目录）。对策：改名必须带迁移逻辑，且迁移要幂等、失败可回滚。
- **P8 原生模块不能从打包归档里加载**。需要显式解包配置，否则启动即崩。

## 改代码的代码（用脚本批量改文件）

- **P11 字符串替换只匹配了一半表达式，把链式调用改断了**。实测：想把 `.join([...].map(x => `${x}/`).join('\n'))` 换成 `.join(profile.ignore.join('\n'))`，替换串漏了开头的 `.join(`，结果变成 `.split(...)` 后直接跟表达式，语法错误。**对策**：① 替换前先打印原文那一行，确认匹配边界；② 改完立刻 `node --check` / `python -m py_compile`；③ 一次只改一处，别在一个脚本里改五个地方。

## 规范与工具本身

- **P12 覆盖钩子会导致检查静默降级**。实测：把项目原有的 `pre-commit`（跑治理检查 + 类型检查）直接替换成模板版本（只有治理检查），提交照样"通过"，但类型错误已经能混进去了。**比没有钩子更危险**——人以为有保护。对策：换钩子前先看原有内容，把项目特有的检查追加到模板钩子末尾。
- **P13 换行符会让「字节预算」和「内容哈希」跨平台不等价**。实测：同一个 `AGENTS.md`，LF 下 11814B，`core.autocrlf=true` 的 Windows 检出是 12029B（正好多出「行数」个字节），预算 12288B 于是从 96% 变成 98%。同理，提交进仓库的 `BOARD.md` 若在 Windows 生成、在 Linux 校验，源哈希必然对不上，被误判成"已过期"。**根因**：规则读的是磁盘原始字节，而原始字节依赖检出的换行策略。**对策**：① 预算按 LF 归一化后计字节；② 内容哈希同样归一化；③ 测试里显式构造 CRLF 夹具，断言与 LF 结果一致——只在 Linux 跑测试永远发现不了。
- **P14 「CI 绿」不等于「本地绿」，两者可能系统性不同**。实测：同一个 commit 的 CI Ubuntu / Windows 任务都是绿的，但同一份代码在真实 Windows 开发机上跑，`test-parity` 必挂——Python 的 stdout 把 `\n` 翻成 `\r\n`，Node 不翻，断言比的是原始字节。**根因**：CI 的 checkout 不启用 `core.autocrlf`，工作区是 LF；开发机默认 `true`，工作区是 CRLF。也就是说 CI 只覆盖了 LF 世界，恰好绕开了这类缺陷，绿得毫无意义。**对策**：① 涉及换行或编码的断言必须显式构造 CRLF 夹具，不能只靠 CI 的默认检出；② 交接结论要写清"在哪个环境验证过"并绑定 commit SHA，本机没复现就标 `unverified`——不要把"CI 绿"直接当成"能跑"。

- **P15 模板把自己的预算吃满，等于锁死使用者**。实测：在真实项目上首次初始化后，`AGENTS.md` 占 12288B 预算的 **99%**，只剩 87B；而 README 明确要求用户「改 §0 四条里跟本项目相关的措辞」——照做就会立刻被自己的闸门拦住。**根因**：模板作者只检查「不超预算」，从没检查「留出余量」；更糟的是 `AGENTS.md` §4 把 `gov.toml` 的白名单又抄了一份，每重跑一次初始化清单就变长一点，文件持续膨胀。**对策**：① 预算类约束必须配「余量下限」，并写成测试（本仓库：初始化后 `AGENTS.md` 至少留 1024B 给项目自有规则）；② 同一事实只留一个家，入口文件只放指针，不复制配置内容。

- **P16 把安装脚本的输出管道给 `head` 会杀死安装进程**。实测：`node init.cjs . | head -3` 让读端提前退出，写 stdout 抛 EPIPE 且无人捕获，进程在事务中途死亡——既没走到回滚也没走到提交，留下 **25 个** `.X.agent-standards-backup-<pid>-<n>` 孤儿和半装完的项目。**根因**：文件写入与终端报告在同一个进程里，报告写不出去就把写入也带走了。**对策**：① 安装类脚本必须忽略 stdout/stderr 的 EPIPE，文件落盘比报告重要；② 想截断输出用 `| tail` 或重定向到文件，别用 `| head`；③ 查残留要扫整棵树，只查根目录会漏掉 `.spec/`、`scripts/`、`policy/` 下的。

## 协作与流程

- **P9 「看起来正常」比报错更危险**。未验证的状态被显示成"正常"，用户会基于错误信息做决定。对策：不确定就标"未验证"。
- **P10 一屏内数字混用多种口径**。用户会问"到底信哪个"。对策：结论行的数字必须互斥且加总等于总数，时间窗增量降为小字。
